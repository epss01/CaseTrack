## The precondition you are implementing against

`CaseDeadlineService::SIXTY_DAY_ENABLED` is `false` because three things were required
before it could safely be `true`:

1. **`cases.is_torture_case` exists** — done (2026-08-19 migration). It is nullable:
   `true`, `false`, or `null` ("not determined," for cases docketed before this field
   existed).
2. **An extension-request/grant field** — NOT done, and its exact shape is not
   specified anywhere in the codebase or docs available to you. Do not invent one.
   See "Stop-and-ask condition" below.
3. **A column recording that a 60th-day RORP was actually filed** — NOT done. Right
   now only `date_fir_submitted` can discharge the 60-day milestone, via the
   "FIR discharges everything" rule in `CaseDeadlineService::statusesFor()`. That is
   not sufficient in isolation for the RORP-specific milestone.

**Do not simply set `SIXTY_DAY_ENABLED = true`.** Doing so today would apply the
torture-case rule to every active case in the office, including the ones where
`is_torture_case` is `null`. That is the exact failure mode the flag exists to
prevent, and it is explicitly called out as worse than leaving the milestone hidden.

## What you are actually building, in order

### Step 1 — Migration: the missing discharge column

Create a new migration adding a nullable `date` column to `case_timelines` for when
the 60th-day RORP was actually submitted. Follow the existing naming and comment
conventions in `case_timelines` migrations (see
`database/migrations/2026_07_24_144751_create_case_timelines_table.php` for style).

Suggested column name: `date_submission_60th_day_rorp`. If you find a better name
already implied elsewhere in the codebase or vault, use that instead and note why in
the migration's docblock. The column must:
- Be nullable (most cases will never set it — it applies to torture cases only).
- Sit near `submission_60th_day` in the table for readability (use `->after(...)`).
- Have a docblock comment explaining it mirrors `date_submission_rop` and
  `date_fir_submitted` as the *actual* discharging event for the 60-day *deadline*.

### Step 2 — Model updates

In `app/Models/CaseTimeline.php`:
- Add the new column to `$fillable` and to the `casts()` date list.
- Add it to `chronologyRules()` with the same `after_or_equal:date_of_docket` rule
  the other milestone dates use.

### Step 3 — `CaseDeadlineService` changes

In `app/Services/CaseDeadlineService.php`, make these changes carefully — this file
is the single source of truth for deadline logic and is covered by the write-guard
hook, so you are the only file allowed to do date arithmetic here:

1. Change the `SIXTIETH_DAY` entry in the private `MILESTONES` array so
   `'discharged_by'` points at the new column instead of `null`.
2. `visibleMilestones()` currently gates the 60th day purely on
   `SIXTY_DAY_ENABLED`. Change this so the 60th-day milestone is visible **only when
   both** `SIXTY_DAY_ENABLED` is true **and** the specific case is a torture case.
   Because `visibleMilestones()` has no per-case context today (it's static and
   milestone-keyed, not case-keyed), you will need to either:
   - Add case-awareness to `statusesFor()` so it can additionally suppress the
     60th-day entry when `$timeline->case->is_torture_case !== true` (note: strict
     `true`, not truthy — `null` and `false` must both suppress it), or
   - Restructure so the torture-case check happens once inside `statusesFor()`
     before the milestone loop.
   Whichever approach you take, preserve the existing guarantee: `visibleMilestones()`
   remains the only thing any caller can use to discover what's shown, and there must
   be no second path into a controller or view that bypasses this check. Update the
   method's docblock to describe the new two-part gate (flag AND case type).
3. You will need `CaseTimeline` to resolve back to its parent `CaseModel` to read
   `is_torture_case`. Check whether `statusesFor()` currently receives a `CaseTimeline`
   with its `case` relation loaded from callers (`AlertController`, `ReportController`,
   `CaseController::show`, etc.) — if not, either eager-load it at each call site or
   pass `is_torture_case` as an explicit parameter instead of reaching through a
   relation that may not be loaded (avoid introducing an N+1 query — check every
   caller of `statusesFor()` and `caseStatusFor()`).
4. Update every docblock in this file that currently states the 60-day milestone is
   "computed but never surfaced" — that description will no longer be accurate once
   this ships, and the class docblocks are treated as authoritative documentation
   throughout this project (they're quoted verbatim in the Obsidian vault reference
   docs). Do not leave stale claims in place.
5. **Leave `SIXTY_DAY_ENABLED` set to `false` for now.** You will flip it only in the
   final step, after tests pass and after the stop-and-ask condition below is resolved.

### Step 4 — Update `visibleMilestones()`'s test coverage assumptions

`tests/Unit/CaseDeadlineServiceTest.php` has tests gated on `SIXTY_DAY_ENABLED` via
`markTestSkipped()`. Once the flag flips these tests will start actually running —
read them now and make sure your implementation will make them pass, don't wait
until the end to find out. Add new tests for the behavior that didn't exist before:
- A torture case (`is_torture_case === true`) past its 60th day with no RORP filed
  is `STATUS_OVERDUE` on that milestone.
- A torture case within the 14-day warning window on the 60th day is `STATUS_DUE_SOON`.
- A torture case with the new column set is `STATUS_SUBMITTED` on that milestone,
  regardless of how overdue the deadline itself is.
- A **non-torture case** (`is_torture_case === false`) never shows the 60-day
  milestone, even far past it with nothing filed — confirm this with the flag on.
- A case with `is_torture_case === null` ("not determined") behaves identically to
  a non-torture case: the 60-day milestone stays hidden. This is the single most
  important test in this whole change — write it explicitly and name it so its
  intent is unmistakable, e.g.
  `test_a_case_with_undetermined_torture_status_never_shows_the_sixtieth_day`.
- `caseStatusFor()` correctly folds an overdue 60th day into the worst-outstanding
  status for a torture case, and correctly ignores it for a non-torture case.

### Stop-and-ask condition — do not skip this

Before you flip `SIXTY_DAY_ENABLED` to `true` anywhere, re-check requirement #2 from
the precondition section: "an extension-request/grant field." Nothing in the files
you were told to read defines what this should look like. There are two readings:

- **(a)** It refers to a 30-day ROP extension mechanism unrelated to the 60-day
  torture-case rule itself (the CHR-answers text mentions "a thirty-day extension
  may be requested" in the context of the ordinary ROP deadline, not the torture-case
  timeline) — in which case it may be out of scope for *this* change entirely, and
  the docblock's "AND" is stricter than the actual business requirement.
- **(b)** It refers to some analogous extension mechanism specific to the 60-day
  RORP deadline that has never been built and isn't described anywhere you have
  access to.

**Do not guess and silently build something for reading (b).** Instead:
1. Implement everything in Steps 1–5 above (this is safe and correct regardless of
   which reading is right, since none of it depends on an extension mechanism).
2. Leave `SIXTY_DAY_ENABLED = false`.
3. Stop, and report back to me directly with:
   - A summary of what you built and why it's safe to ship as-is.
   - The exact ambiguity above, in your own words, so I can either confirm reading
     (a) — in which case you'll flip the flag in a follow-up — or tell you what CHR
     actually meant so you can build it properly.
   - Add a `ponytail: SIXTY_DAY_ENABLED remains false pending clarification on the
     "extension-request/grant field" requirement — see [this session's summary] —
     flip once resolved.` comment directly above the `SIXTY_DAY_ENABLED` constant so
     this isn't lost.

If I explicitly tell you in this same session to proceed with reading (a) and flip
the flag now, then and only then: change `SIXTY_DAY_ENABLED` to `true`, remove the
now-obsolete `ponytail:` comment, and re-run the full suite one more time before
finishing.
